サイトを軽く保つ努力は、たいてい三ヶ月で終わる。最初の一週間は嬉しくてバイト数を数えるが、
機能を足すたびに少しずつ増え、ある日 Lighthouse を開いて青くなる。意思の問題ではなく、
仕組みがないだけだ。

そこでこのサイトでは、**1 ページあたりの転送量に上限を決めて、超えたらビルドを失敗させる**
ようにした。テストが落ちるのと同じ扱いにすれば、増えたその日に気づける。

ついでに、測った数字をそのページ自身に印字することにした。フッターに出ている
`Transfer` と `Document` は、いま読んでいるこのページを実測した値だ。

## 何で測るか

Cloudflare は静的アセットを Brotli で配信するので、gzip ではなく Brotli で測る。
Node には最初から入っている。

```js
import { brotliCompressSync, constants } from 'node:zlib';

const transfer = brotliCompressSync(html, {
  params: { [constants.BROTLI_PARAM_QUALITY]: 11 },
}).length;
```

測るタイミングはビルドの最後、`dist/` が出来上がった後。ここなら HTML の圧縮も
CSS のインライン化も済んだ、実際に配信されるバイト列そのものを見られる。

## 自分を測ると目盛りが動く

ここで問題が起きる。**数字を埋め込むとファイルの中身が変わり、サイズも変わる。**
体重計に乗ったら目盛りが動くようなものだ。

非圧縮バイト数のほうは簡単に潰せる。プレースホルダを **10 文字固定**にして、
置換する文字列も 10 文字に右詰めすればいい。長さが変わらないので、
置換前に測ったサイズは置換後のサイズと 1 バイトも違わない。余った空白は
HTML の空白圧縮で見えなくなる。

Brotli 後のサイズはそうはいかない。中身が変われば圧縮率が変わる。
これは要するに `f(v) = v` を満たす `v` を探す問題なので、素直に反復する。

1. いまの値で置換してみる
2. 置換後のサイズを測る
3. 測った値がさっき埋めた値と違えば、それを新しい値にして 1 に戻る

半分くらいのページはこれで一致する。残りは 2 周期に落ちて止まらない。
`4,410` を埋めると `4,411` になり、`4,411` を埋めると `4,410` になる、という振動だ。
不動点をちょうど跨いでいて、この写像には解が存在しない。

## 自由度をひとつ足す

解がないなら、写像のほうを少し変えればいい。

このページのメーターは `--ratio` という CSS 変数で幅を決めている。
その小数点以下の桁数は、**表示にはまったく影響しない**。`0.5382` でも `0.538` でも
バーの見た目は 1 ピクセルも変わらない。けれど文字列としては違うので、
圧縮後のサイズは変わる。

つまりここに、誰にも見えない自由度がひとつある。桁数を 4 → 3 → 2 → 5 と回して
写像を少しずつずらし、`f(v) = v` が成り立つ組み合わせを探す。

```js
for (const digits of [4, 3, 2, 5]) {
  const value = findFixedPoint(digits);
  if (isExact(value)) return value;
}
```

15 ページ全部で厳密解が見つかった。表示されている数字は、いま配信されている
このファイルを Brotli にかけた結果と、1 バイトも違わない。

## 予算をいくつにするか

このサイトは 8 KiB にした。いま一番重い記事で 5.2 KB なので、まだ 3 割以上空いている。

余裕のある予算には意味がない、という考え方もある。ただ予算の役目は切り詰めることではなく、
**増えたことに気づくこと**なので、これでいい。ある日 4 KB が 7.8 KB になっていたら、
何かがおかしいと分かる。
